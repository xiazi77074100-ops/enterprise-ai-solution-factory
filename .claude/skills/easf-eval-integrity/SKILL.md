# easf-eval-integrity — 評価と実験の公正さ

正本は `easf_package/docs/03_ACCEPTANCE_AND_EXPERIMENT.md`・`07_DATA_AND_EVAL.md`・`prompts/03_BASELINE_EXPERIMENT.md`。

## 1. 合成データ

- 会社名・人名・住所・電話・口座はすべて架空。実在の会社名・実在しうる口座番号を使わない。登録番号は `T` ＋ 13 桁の形式で、文書とラベルに「TEST ONLY」の印を付ける。
- 実在の請求書・契約書の様式（著作物）を写さない。生成器（`fixtures/generator/`）と乱数の種・生成器の版を記録し、同じ入力から同じ文書が作れるようにする。
- 各業務 30〜50 件。層：通常、項目・条項の欠落、あいまいな表現、金額・条項の矛盾、複数ページ、回転・低品質の画像、表、和暦、OCR の雑音、同じラベルの重複、**埋め込まれた不審な指示**（`jp-secure-coding` ai-llm-mcp.md §1）。
- 法的助言にならないよう、契約のポリシーは架空のものと明記する。

## 2. 分割と凍結

1. 実装の調整を始める前に、`dev` と `holdout` に層別で分ける（ホールドアウトは各業務 10 件以上）。
2. `fixtures/manifest.json` に全文書の `sample_id`・`split`・`source_file_sha256`・生成器の版・種を書き、manifest 自体の SHA-256 を `DECISIONS.md` に記録する（凍結）。
3. **ホールドアウトの正解ラベルはリポジトリに置かない**。リポジトリの外（例：人間だけが読む暗号化 ZIP、または別の非公開の場所）に置き、評価のときだけ人間が渡す。リポジトリにはラベルのハッシュだけ。
4. AI（CC・Codex）にホールドアウトのラベル・ホールドアウトでの誤りの詳細を見せない。見えてしまったら作業を止め、`DECISIONS.md` に記録し、人間が新しいホールドアウトを作るか判断する。
5. 凍結後に閾値・ホールドアウト・成功の定義を変えない。変えるなら変更要求と、変更前の結果も残す。

## 3. 正解ラベルの書式

`sample_id, scenario, split, source_file_sha256, gold_fields, gold_findings, gold_evidence(page, start, end, text_sha256), severity, annotator, reviewed_by, policy_version`。値が無いことは `null` と `"missing"` / `"unknown"` を区別する。重大ラベルはできる限り 2 回確認。

## 4. 評価の報告

- 項目：項目ごとの完全一致・正規化一致、マクロ・マイクロ平均、重大項目の見逃し率、ルールの適合率・再現率（重大度別）、根拠の位置の正しさ、確認の記録の完全さ、実行の成功・失敗の分布、人の時間、LLM の費用。
- **誤りの具体例**（誤検出・見逃し）を必ず載せる。平均だけにしない。
- 評価はデータセットの版（manifest のハッシュ）、解決策のハッシュ、モデルと版、Rule pack の版を記録し、再実行できるようにする。非決定的な部分は明記する。
- 閾値は G0 で事前登録したものだけで合否を判定する。

## 5. ベースライン比較

- ベースライン（AI Coding のみ）は**別のリポジトリ・別のセッション**で行い、Factory の Catalog・Composer・評価コード・Capability を使わない。一般的な OSS とふつうの部品リポジトリは使ってよい。
- 両方に同じ凍結済みの要件・受入条件・テストデータ・環境・モデル予算。
- 記録する人の時間：分析・プロンプト・コードレビュー・デバッグ・テスト設計・統合・QA・報告（`HUMAN_TIME_LOG.csv` の arm を分ける）。AI の費用も arm ごと。
- 学習効果（同じ人が両方を行う）・順序・人数の少なさは「妥当性への脅威」として必ず書く。
- 比較は「2 件目の案件の追加工数」と「Factory を作る費用を含めた総費用」の両方。損益分岐は分母が正で前提を説明できるときだけ計算する。
- 30% に届かなければ、届かなかったと書き、部品ライブラリ＋手順書への方向転換を検討事項として出す。
