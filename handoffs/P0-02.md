# 引き渡し P0-02：Phase 0 の独立レビュー（アーキテクチャ・セキュリティ・契約）

| 項目 | 内容 |
|---|---|
| 実施者 | **CC が代行**（D-011。Codex が使えないため。自己レビューの制約は D-012） |
| フェーズ / ゲート | Phase 0 / G0 |
| ブランチ | `cc/P0-02-g0-review`（main の最新から） |
| 前提 | `easf_package/prompts/01_CODEX_PARALLEL.md` の「Initial action (phase 0 only)」 |

## 目的
CC が作った Phase 0 の成果物を、実装担当と独立した立場で疑ってかかり、G0 を止めるべき問題（BLOCKER）を見つける。

## 入力（読むもの）
- `easf_package/` 全部（仕様の正本）
- `AGENTS.md`、`.claude/skills/`（特に `jp-secure-coding`・`jp-vuln-assessment`・`easf-capability-contract`）
- `docs/phase0/PHASE0_PLAN.md`、`DECISIONS.md`、`docs/adr/ADR-001〜009`
- `contracts/`（スキーマ・OpenAPI・examples）、`docs/design/basic/architecture.md`、`docs/design/security.md`

## 出力（作るもの）
`reviews/G0_REVIEW.md`（日本語）：
1. 仕様と成果物の矛盾、抜けている受入条件、危ない前提、代わりの案。
2. 独立テストの観点表（請求書・契約書・Workflow・アダプタ・認証・人の確認・根拠の完全性・LLM ポートの切り替え）。
3. 文書の業務 2 つで再利用の一般性を言いすぎていないかの評価。
4. 契約 v1 の確認：`python scripts/validate_contracts.py` を実行し結果を貼る。さらに、契約で表せない・表しにくいケース（例：配列の明細の検証、OCR 由来の根拠、確認の差し戻し後の再実行）を挙げる。
5. 指摘一覧（`jp-dev-standards` のレビュー指摘票の形式。区分 BLOCKER / MAJOR / MINOR / 質問）。

## 変えてよいパス
- `reviews/G0_REVIEW.md` だけ

## 変えてはいけないパス
- それ以外すべて（直すべき点は指摘票に書く）

## 受入条件
| 条件 | 確かめ方 |
|---|---|
| 指摘ごとに場所（ファイル・節）と理由と修正案がある | 指摘票 |
| 実行したコマンドと出力を貼っている／実行できなかったものは理由 | 本文 |
| BLOCKER の有無を明記 | 冒頭の総評 |

## 記録
`HUMAN_TIME_LOG.csv`（人がレビューに使った時間：arm=`shared`、task_id=`P0-02`）。

## 提出
PR の説明：範囲・実行したコマンドと結果・BLOCKER の数。マージはしない。STOP。
