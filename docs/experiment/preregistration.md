## 1. 問い

同じ人と同じ AI Coding の道具（Claude Code / Codex）で、**2 件目の業務（契約書レビュー）の POC を作る人の作業時間**は、Factory を使うと、使わない場合より 30% 以上少なくなるか。品質と安全は劣らないか。

## 2. 2 つの arm

| | ベースライン（A） | Factory（B） |
|---|---|---|
| 道具 | Claude Code / Codex、一般的な OSS、ふつうの部品リポジトリ | 同じ ＋ EASF（Catalog・Composer・Executor・評価・既存の Capability 版） |
| 使ってはいけないもの | EASF のコード・契約・Capability・Rule pack の JSON・評価コード・skill の `easf-*` | holdout の文書・正解 |
| 作業場所 | **別リポジトリ**（`easf-baseline-contract`、非公開）、**別セッション**（EASF の会話・メモリを持ち込まない） | EASF リポジトリ |
| 要件 | 凍結済みの要件パッケージ（§3）を渡す | 同じ |
| LLM | 同じプロファイル（mock、または承認後の同じ実 API・同じモデル）、同じ予算 | 同じ |

## 3. 凍結する要件パッケージ（両 arm に同じものを渡す）

- 業務の説明：`easf_package/docs/01_PRD.md` §6（契約書レビュー）
- 抽出する項目：`contracts/examples/workflows/contract.json` の `field_spec` を **文章の表** に書き直したもの（JSON は渡さない）
- 確認ポリシー：`contracts/examples/rule_packs/contract-1.0.0.json` の CON-001〜005 を **文章** に書き直したもの（Factory の Rule pack の形式は渡さない）
- 受入条件：AC-06・AC-07・AC-09・AC-12 と、ADR-007 の閾値
- dev データ：`fixtures/dev/` の契約書 28 件と正解（両 arm 同じ）
- 画面：日本語。確認・修正ができ、根拠を表示できること（見た目の作り込みは評価しない）

パッケージは Phase 4 の前に `experiment/baseline_bundle/` として作り、SHA-256 を `DECISIONS.md` に記録してから渡す。

## 4. 実施順序（ADR-008）

1. Phase 3：Factory で請求書（1 件目）を作る。
2. **ベースライン（A）で契約書を作る**（別リポジトリ・別セッション）。
3. Phase 4：Factory（B）で契約書を作る。
4. 両 arm で同じ要件変更（§6）を行う。
5. 人が holdout で両 arm を評価する。

## 5. 測るもの

| 指標 | 定義 | 種別 |
|---|---|---|
| M1 追加の人の時間（分） | §4 の 2（A）と 3（B）の人の作業時間の合計。`HUMAN_TIME_LOG.csv` の activity：analysis・prompting・code_review・debugging・test_design・integration・qa・reporting。`waiting` は別に記録し合計に入れない | **主要** |
| M2 要件変更の人の時間（分） | §6 の作業の人の時間 | 副次 |
| M3 品質 | holdout での ADR-007 の全指標 | 非劣性の判定 |
| M4 AI の費用（円） | arm ごとの API・ツールの費用（`COST_LEDGER.csv` の arm） | 副次 |
| M5 経過時間 | 着手から受入までの暦の時間 | 参考 |
| M6 総費用 | Factory を作る時間（Phase 1〜3 の人の時間）＋保守を含めた比較（§7） | 副次 |

記録の規則：作業の開始・終了ごとに 5 分単位で記録。中断は記録を止める。迷う作業は note に内容を書き、分類は後で変えない。

## 6. 要件変更（両 arm 同じ）

- **CR-1（契約書）**：新しい項目「反社会的勢力の排除条項」を抽出し、無ければ critical として確認へ回すルールを追加する。
- **CR-2（請求書）**：新しい項目「源泉徴収税額」を抽出し、記載があれば「差引支払額＝合計−源泉徴収税額」と一致するかを確認する（major）。

CR-2 はベースライン側に請求書の実装がないため、ベースラインは「請求書の最小実装を同じ要件で別に用意したもの」に対して行うか、CR-2 を比較から外して参考値とする。**決定（D-016）：CR-2 は参考値とし、比較は CR-1 だけ。**

## 7. 判定

- **成功**：M1 で `B ≤ 0.7 × A`、かつ M3 で次の非劣性をすべて満たす。
  - 重大な誤りの黙認：両 arm とも 0 件（B が 1 件以上なら不成功）
  - 重大ルールの再現率：B が 1.0
  - 項目抽出（正規化一致のマクロ平均）：B ≥ A − 0.05
  - 根拠の位置の正しさ：B ≥ 0.9
- **不成功**：上のどれかを満たさない。結果をそのまま報告し、「部品ライブラリ＋手順書」への方向転換を検討事項として出す。
- 損益分岐の案件数：`ceil((Factory の構築＋保守の人の時間) / (A − B))`。`A − B ≤ 0` のときは計算しない。前提（時間単価を使わず人の時間で比べる、保守の見込み）を併記する。
- 件数が 1 回ずつの比較なので、差の大きさと不確かさ（学習効果など §9）を必ず並べて書く。

## 9. 妥当性への脅威（報告に必ず書く）

| 脅威 | 向き | 対策・扱い |
|---|---|---|
| 同じ人が両 arm を行う学習効果（A を先に行うため、B は 2 回目） | B に有利 | ADR-008。報告で明記。CR-1 は両 arm とも初めてなので比較の補強になる |
| Factory の設計者が実験を設計した（本書は CC が作成） | B に有利 | 人が承認時に A に不利な条件がないか確認。要件パッケージは文章にして渡す |
| AI の会話・記憶の持ち込み | B に有利（A に Factory の知識が漏れれば A に有利） | A は別リポジトリ・新しいセッション、EASF のファイルを開かない |
| 件数の少なさ（holdout 12 件、比較 1 回） | 不明 | 統計的な主張をしない |
| 時間の記録の誤差 | 不明 | 5 分単位、分類の定義を固定 |
| 道具・モデルの更新 | 不明 | 両 arm で使った版を記録 |
