# セキュリティ設計（脅威モデル）

| 版 | 日付 | 変更内容 | 作成者 |

実装の規則は `jp-secure-coding`、確かめ方は `jp-vuln-assessment`。ここは「何を守り、何が脅威で、どこで止めるか」。

## 1. 守るもの

| 資産 | 重要な理由 |
|---|---|
| 判定の正しさ（金額・振込先・契約の重大条項） | 黙って誤ると業務の損害につながる（POC でも評価の主目的） |
| 確認の記録（誰がいつ何を直したか） | 監査・再現性 |
| 不変の版・凍結したデータセット・閾値 | 再利用と評価の証拠 |
| 認証情報・セッション・API キー | 乗っ取り・費用の不正利用 |
| ホールドアウトの正解 | 評価の公正さ |
| 費用の上限 | 予算 10,000 円 |

## 2. 信頼の境界

1. ブラウザ ⇔ API（利用者の入力、アップロード）
2. API ⇔ ワーカー ⇔ 解析の子プロセス（文書の中身）
3. ワーカー ⇔ LLM 提供元（文書を送る・出力を受ける）
4. ワーカー ⇔ MCP サーバ（ツールの応答）
5. 設定ファイル・環境変数（秘密・接続先）
6. 開発者・AI エージェント ⇔ リポジトリ（ホールドアウト・秘密・会社の資産の混入）

## 5. ゲートのセキュリティ条件

`jp-vuln-assessment` §2：高・中 0 件（受容は人の承認が必要）、SCA の高・重大 0 件、秘密の検出 0 件。G1a から毎ゲートで自己診断を行う。

## 6. 予期しない例外のログ（VA-G4-001）

`backend/app/core/middleware.py` は予期しない例外を捕捉した際、例外オブジェクト・本文・原因・SQLパラメータ・スタックトレースをロガーへ渡さない。固定の書式に例外型と、サーバが発行したtrace_idだけを記録し、構造化フィールドの `error_type`・`trace_id` にも同じ値を残す。標準のテキスト表示でも型とtrace_idを確認できる。完全なスタックトレースの代わりに、応答と同じtrace_idで追跡する。

HTTPの500応答、エラーコード `internal_error`、利用者向け文言、セキュリティヘッダは変更しない。再発防止は `backend/tests/security/test_error_logging.py` の通常・連鎖・SQLAlchemy例外の合成3ケースで確認する。これは全ログ・全例外経路・配備環境のログ権限や保持期限を確認したことにはならない。
