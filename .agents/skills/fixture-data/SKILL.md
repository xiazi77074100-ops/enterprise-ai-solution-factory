# fixture-data — 合成データの整合ルール

sales-assistant の `demo-mock-data`（2026-10-14 版）の整合ルールを、EASF の合成文書・正解ラベル向けに書き直したもの。
**文書の見た目・正解ラベル・画面の集計が、同じ事実を指していること**が最優先。正解とずれた文書は評価そのものを壊す。

## 1. 単一の正と派生

| 事実 | 正（ここだけで持つ） | 派生させる側 |
|---|---|---|
| 1 件の請求書・契約書の内容 | 生成器の **レコード**（`fixtures/generator/` が作る構造化データ） | PDF・画像（レンダラ）と正解ラベル（`gold_fields`）を **同じレコードから** 作る。ラベルを手で書き写さない |
| 正解の根拠の位置 | レンダラが配置した文字の範囲（ページ・開始・終了） | `gold_evidence` とその `text_sha256`。描画後のテキスト抽出で照合するテストを置く |
| ルールの正解（`gold_findings`） | レコードに付けた「仕込み」（合計の不一致・登録番号の欠落・条項の欠落など）の一覧 | 期待される `rule_id` と重大度。仕込みの無い文書は該当なし |
| 合計・税額 | 明細と税率から計算 | 「矛盾」層だけ、計算値からわざとずらし、ずらした量をレコードに記録 |
| 文書の層（通常・欠落・あいまい・矛盾・…） | 生成の計画（`PLAN`） | manifest の `stratum`。層の件数は計画と一致 |

## 2. 日付

- すべて固定の基準日（`BASE_DATE`、生成器の設定）からの相対で作る。生成器・テスト・ラベルに日付を直書きしない。
- 請求日 ≦ 支払期日、契約の開始日 ≦ 終了日、通知期限は終了日より前。わざと矛盾させる層だけ例外にし、レコードに印を付ける。
- 和暦・スラッシュ・漢数字の表記は、同じ日付の **表記の違い** として作り、正解は西暦の `date`。

## 3. 名前・番号のリアルさと印

- 会社名は「屋号＋業種の語＋法人格」で、業種と社名を合わせる。英字・「サンプル」・連番の付いた名前を作らない。**実在の会社名と一致しないことを確かめる**（一覧と突き合わせる簡易チェック）。
- 人名は架空。住所・電話は実在しない形（例：市外局番の範囲外など、方針は生成器に記録）。
- 登録番号・口座番号は形式だけ正しい架空の値。文書の欄外とラベルに **「TEST ONLY」** を必ず入れる（名前はリアルに、番号と文書は偽物と分かるように）。
- 同名の別会社など紛らわしい例は、意図した組だけを計画に書いて作る。
- 「埋め込まれた不審な指示」の文面は数通りから選び、どの文書に入れたかをレコードに記録する。

## 4. 集計と画面

- 画面のタイル・件数（例：「確認待ち 3 件」）は、クリック先の一覧と **同じ条件関数**（サーバの同じクエリ）で数える。件数＝遷移先の行数。
- 評価の数値は評価結果（`EvaluationRun`）からだけ出す。画面で計算し直さない。
- ロールの範囲（自分の案件だけ）は一覧・タイル・集計で同じ関数を使う。

## 5. 乱数列を守る

- 乱数は固定シード。生成器の版とシードを manifest に記録する。
- 既存の文書を変えるときは、他の文書の値が変わらないようにする：乱数の呼び出し回数を変えない（使わなくなった値も引いて捨てる）、新しい文書は計画の末尾に足す。
- **凍結後の dev・ホールドアウトの文書は作り直さない**。作り直すなら新しいデータセットの版にする（`easf-eval-integrity`）。

## 6. 確認手順

1. 生成器のテスト：レコード → 文書 → テキスト抽出 → 正解の根拠の範囲が一致、層の件数が計画どおり、日付の順序、実在名の突き合わせ、TEST ONLY の印。
2. manifest の SHA-256 が記録と一致（凍結後）。
3. 画面の集計を変えたら、各ロールでタイルをクリックし、件数と一覧の行数が一致するかを Playwright で確かめる。
4. 生成の方針を変えたら `spec-sync` で設計書（`docs/design/fixture_plan.md`）も同じコミットで直す。
