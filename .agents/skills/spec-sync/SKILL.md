# spec-sync — 設計書をコードと同じコミットで直す

sales-assistant の `demo-spec-sync`（2026-10-14 版）の手順を EASF 向けに書き直したもの。
EASF では **契約（`contracts/`）が正、コードはそれに従い、設計書は両方を説明する**。契約・コード・設計書のどれか 1 つだけが変わったコミットを作らない。

## 直す場所

| 変更の種類 | 直す場所 |
|---|---|
| 画面の追加・削除、メニュー・表示ロールの変更 | `docs/design/basic/screens.md`（画面一覧・遷移）、`permissions.md`（権限表） |
| API の追加・変更・削除 | **先に `contracts/openapi.yaml`（CC だけ）**、次に `docs/design/basic/api.md` |
| データ項目の追加・削除・型や選択肢の変更 | `docs/design/detail/data.md`（項目定義）、マイグレーション（CC だけ） |
| 操作の追加・変更（作成・更新・削除・状態遷移・承認・エクスポート） | 該当機能の「操作」表（誰が／入力／チェック／副作用／API） |
| 入力チェック・エラーメッセージ | 該当操作の「チェック」列（文言はコードからそのまま写す） |
| 状態遷移（実行・ノード・確認タスク・解決策） | `docs/design/detail/state_machines.md` |
| 権限の判定 | `permissions.md` と認可のテスト（ロール × エンドポイントの期待値表） |
| ルール・評価の計算式・閾値 | `docs/design/detail/rules_and_metrics.md`（閾値は凍結後に変えない。`easf-eval-integrity`） |
| エクスポートの列・イベントの項目 | `docs/design/detail/exports_and_events.md`、`contracts/events.schema.json` |
| 模擬・簡略化の追加・削除 | `docs/design/basic/limitations.md` |

## 手順

1. 変更前に該当する設計書の節を読む。
2. 契約を変えるなら、所有者（CC）が契約を先に直し、版を上げる（`easf-capability-contract` §6）。Codex は変更要求として出す。
3. コードを変える。
4. 設計書を **変更後のコードと契約** に合わせて書き換える。項目名・選択肢・エラーメッセージはコードの表記をそのまま使う。根拠のファイルを `backend/app/xxx/yyy.py` の形で添える（行番号は付けない）。
5. 設計書の冒頭の改版履歴に 1 行：`| 版 | YYYY-MM-DD | 変更内容 | 作成者 |`。
6. 契約・コード・設計書・テストを同じコミットに入れる。

## 書き方

- 事実だけ。コードに無い振る舞いを推測で書かない。決まっていないことは「未決事項」へ。
- 1 操作 1 行。長い説明は表の下に箇条書き。
- 用語は画面の表記と用語集（`docs/design/glossary.md`）に合わせる。
- 削除した機能は節ごと消し、改版履歴に「削除」と残す。
